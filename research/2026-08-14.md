# Research snapshot — 2026-08-14

This dated file records design evidence only. The skill must **not** treat any package version, library name, browser capability, or API detail captured during development as permanently current.

## OpenAI plugin packaging baseline

The implementation baseline uses a skill-only plugin with `.codex-plugin/plugin.json`, a skill under `skills/<skill-name>/SKILL.md`, supporting references/scripts, and a repository marketplace entry under `.agents/plugins/marketplace.json`.

Packaging details are version-sensitive product behavior. Re-check current first-party OpenAI documentation before changing packaging assumptions.

## Universal package-resolution finding

The npm registry is queried by package name at execution time. There is no technical requirement for this plugin to maintain a predefined list of recognized 3D packages in order to fetch public registry metadata.

The architectural consequence is important:

- explicit `--package <name>` input must accept arbitrary npm package names;
- `--project <path>` must derive names from the inspected manifest rather than a plugin-owned allowlist;
- peer dependencies, engines, deprecation state, type-declaration strategy, optional feature packages, loaders/codecs/workers, and related tooling are discovered from the actual package/project rather than encoded as fixed ecosystem knowledge;
- packages unavailable from the selected registry must fail visibly rather than being silently omitted;
- alternate/private npm-compatible registries can be selected with `--registry`, subject to the execution environment's actual authentication/access.

Representative packages used during tests are test data only. They are not a supported-package catalog and must never be promoted into production routing rules.

## General compatibility/standards findings

- Runtime packages and TypeScript declarations are separate compatibility surfaces; whether supplemental declarations are required must be determined from the actual package and compiler configuration.
- Browser/device capabilities can be present at one detection layer yet fail during initialization; optional graphics/XR capabilities require real capability checks and explicit failure handling.
- Browser-only graphics initialization must respect the project's real client/server/runtime boundary.
- Asset processing and runtime delivery are separate concerns; required extensions, codecs, workers, decoders/transcoders, base paths, and production URLs must be verified from the concrete pipeline/deployment.
- Hardware-specific success cannot be claimed without evidence from the relevant hardware/environment.
- Standards-sensitive work should use current first-party/normative sources rather than proposal-era snippets or remembered API state.

## Integration verification policy

- Resolver integration tests use the real public npm registry at `https://registry.npmjs.org`; no loopback HTTP server or fabricated package metadata is accepted as proof of external integration.
- Tests exercise arbitrary explicit package input and project-derived dependency input rather than a maintained ecosystem list.
- Current version numbers are not asserted as constants. Tests compare resolver results with live registry responses at execution time so legitimate future releases do not create false failures.
- Node's built-in `fetch()` implementation is used with explicit HTTP success checks and bounded request timeouts.
- A real service outage is reported as a failed integration check; the suite does not substitute simulated success.

## Source policy

For any newly discovered package or technology, use the package maintainer's current official documentation, release notes, upstream source/API reference, and registry metadata as applicable. For browser/platform behavior use current MDN plus relevant normative W3C/Khronos standards where applicable. The source set is intentionally open-ended because the plugin is not limited to technologies known when this repository was authored.
