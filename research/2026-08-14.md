# Research snapshot — 2026-08-14

This dated file records design evidence only. The skill must **not** treat any package version, library name, toolchain, engine/editor release, platform capability, or API detail captured during development as permanently current.

## OpenAI plugin packaging baseline

The implementation baseline uses a skill-only plugin with `.codex-plugin/plugin.json`, a skill under `skills/<skill-name>/SKILL.md`, supporting references/scripts, and a repository marketplace entry under `.agents/plugins/marketplace.json`.

Packaging details are version-sensitive product behavior. Re-check current first-party OpenAI documentation before changing packaging assumptions.

## Second universality stress audit

A second adversarial audit tested the architecture conceptually against substantially different real-world project models. The probe projects were deliberately not encoded into plugin behavior or permanent user journeys. Their purpose was to discover cross-cutting assumptions.

The audit exposed four architectural defects in version 1.1.0:

1. **Language/runtime eligibility gating.** Skill and plugin discovery text still described JavaScript/TypeScript and web-oriented work, so a non-web or non-JS project could fail to trigger the plugin despite being valid 3D/graphics engineering.
2. **npm/package.json provenance assumptions.** The source policy and helper implied a public package registry was the universal dependency model, even though projects can source dependencies from registries/indexes, VCS revisions, local/workspace paths, vendored source, SDKs/frameworks, system installations, engine/editor package systems, generated artifacts, or other mechanisms.
3. **Single-manifest assumptions.** Real repositories can be multi-root/polyglot and can contain several independently resolved dependency/build graphs, generated bindings, native boundaries, editor-managed files, and multiple deployment targets.
4. **Web-heavy verification invariants.** The prior invariant set underrepresented compiler/interpreter, SDK, compile/link/ABI/architecture, shader-build ownership, generated/editor-managed state, signing/package distribution, driver/runtime, and native hardware concerns.

The correction is **not** a list of supported ecosystems. The core architecture is now project-first and provenance-first. Ecosystem-specific helpers can exist only as optional conveniences after project evidence proves they apply.

## Authoritative evidence for non-uniform project models

Current first-party documentation confirms that common developer ecosystems do not share one universal dependency/build model:

- Cargo supports dependencies from registries, alternate registries, Git repositories, and paths/workspaces.
- CMake supports dependency discovery and dependency providers around externally built or locally supplied components rather than a single central package-manifest model.
- Unity stores package-manager project state in project manifests and supports package sources beyond a public npm-style registry, including project/editor-managed package mechanisms.
- Python packaging metadata can declare normal dependencies while installers also support direct references such as VCS URLs, archives, and local paths.
- Swift Package Manager supports remote package dependencies and also system/binary dependency models.
- Metal shader code can participate in build-time compilation pipelines and produced libraries/artifacts, so shader source, compiler/toolchain, target device/runtime, and generated output ownership are separate correctness surfaces.

These examples are evidence for the generalized provenance model only. They are **not** encoded as supported-ecosystem routes.

## npm helper correction

npm remains useful for npm-compatible projects, but the helper is now explicitly scoped:

`skills/current-3d-engineering/scripts/resolve-npm-packages.mjs`

The previous ambiguous `resolve-packages.mjs` name was removed so no executable implies that npm metadata is the plugin's universal dependency resolver.

Current npm documentation also demonstrates why provenance classification is necessary inside npm projects themselves. Dependency specs can represent normal registry versions/ranges, `npm:` aliases, Git/VCS sources, remote URLs, local files/directories, and other forms. Therefore project mode now:

- queries real npm-compatible registry metadata only for registry-backed specs;
- resolves an `npm:` alias against the target registry package while preserving the project's declared alias and original spec;
- preserves local/workspace/VCS/protocol specs as `nonRegistryDependencies` instead of issuing false public-registry requests;
- reports real registry-backed failures visibly;
- keeps arbitrary explicit `--package <name>` support with no recognized-package allowlist.

npm-specific semantic-version and `dist-tags` logic remains inside this helper only. It is not promoted into the universal source policy.

## Universal project evidence model

Before changing a project, the skill now discovers evidence by responsibility rather than requiring known filenames:

- relevant project root(s), workspaces, subprojects, modules, packages, or build targets;
- dependency declarations and resolved state plus actual dependency provenance;
- compiler/interpreter, language mode, SDK/toolset, engine/editor, build system, and platform versions;
- source imports/includes/references and runtime entry points;
- generated, vendored, editor-managed, cached, binary, or authoritative-source ownership;
- build, tests, static analysis, shader compilation, packaging, signing, deployment, and CI paths;
- runtime/process boundaries and target OS/CPU/GPU architecture, graphics API, drivers/runtimes, and hardware constraints;
- assets, shaders, native libraries/plugins/modules, generated bindings/binaries, codecs, and other non-source dependencies.

Unknown technology triggers discovery and first-party research rather than rejection or substitution.

## Version/release semantics

The universal policy no longer defines stable as a semantic version. Version/release semantics come from the actual project and ecosystem. The agent preserves exact pins, VCS revisions, lock/resolution state, SDK/toolchain versions, engine/editor releases, compatibility ranges, and release channels unless the requested change requires them to move.

A newer package/version/commit/SDK/toolchain is not automatically better. Compatibility must be proven for the real project.

## Expanded engineering invariants

The invariant set now covers, when applicable:

- dependency provenance and compatibility;
- compiler/interpreter, SDK/toolset, build configuration, and language standard/edition;
- compile vs link correctness, ABI/calling convention, architecture/target triple, binary format, symbols, linkage, and loader/search paths;
- generated/editor-managed/vendor ownership;
- shader preprocessing/cross-compilation/offline/runtime compilation and target backend/device compatibility;
- runtime ownership, concurrency, resource lifetime, time/simulation, and capability/fallback behavior;
- asset/content pipelines, native plugins/libraries, packaging/distribution/signing/permissions;
- cross-language bindings/interfaces and serialization/data-layout ownership;
- performance evidence on the actual CPU/GPU/device/driver/build configuration;
- verification across every affected workspace/subproject/target boundary.

Only applicable invariants are used; there is no requirement to force native, web, engine, or package-manager concerns onto projects that do not expose them.

## Integration verification policy

- External integration claims use the actual authoritative endpoint/environment; loopback or fabricated payloads are not accepted as proof.
- npm helper integration tests use the real public npm registry at `https://registry.npmjs.org`.
- Tests exercise arbitrary explicit registry package input, project-derived registry dependencies, npm aliases, and non-registry dependency preservation rather than a maintained package catalog.
- Current package version numbers are not asserted as constants. Live tests compare helper results with independent registry responses at execution time.
- Node's built-in `fetch()` is used with explicit HTTP success checks and bounded request timeouts.
- A real service outage is reported as a failed integration check; the suite does not substitute simulated success.

## Source policy

For newly discovered technology, select authoritative evidence from its actual provenance and role: project-local resolution/source, registry or index when applicable, VCS/upstream repository, SDK/platform or engine/editor documentation, first-party release/API documentation, or normative standards as appropriate. No particular language, package registry, engine, editor, browser documentation site, or standards body is a universal support gate.
