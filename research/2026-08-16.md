## MCP transport and protocol

Authoritative sources:

- Model Context Protocol `2026-07-28` Streamable HTTP specification: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx
- Model Context Protocol `2026-07-28` schema: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts
- Model Context Protocol `2026-07-28` GA notes: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-07-28-spec-ga/index.md

Verified implementation facts:

- `2026-07-28` is stateless at the protocol layer: there is no protocol initialization handshake or hidden session requirement; `server/discover` provides optional capability discovery.
- Every modern Streamable HTTP POST carries the protocol version and client capabilities in request `_meta`.
- Modern HTTP requests require `MCP-Protocol-Version` and `Mcp-Method`; named calls such as `tools/call`, `resources/read`, and `prompts/get` also require `Mcp-Name`.
- The mirrored HTTP metadata must match the JSON-RPC body. Header mismatch uses JSON-RPC error `-32020`; unsupported modern protocol version uses `-32022`.
- Streamable HTTP uses one POST endpoint. A successful request can return a JSON object; a persistent server-initiated SSE endpoint is not required by the current stateless model.
- Current compatibility still matters. The server also implements the `2025-11-25` initialization-era Streamable HTTP path (`initialize` / `notifications/initialized`) because deployed client implementations may negotiate or fall back to that protocol revision.
- `tools/call.params.arguments` is optional. The v1.4.0 contract therefore accepts omitted arguments for the parameterless `current_3d_info` tool.

The public MCP intentionally implements only the request subset it advertises: discovery/initialization, ping, tools/list, tools/call, resources/list, and resources/read. It does not claim unsupported subscriptions, prompts, tasks, sampling, elicitation, roots, or server-initiated behavior.

## Current Codex plugin packaging

Authoritative sources:

- OpenAI Codex plugin creator scaffold: https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/plugin-creator/scripts/create_basic_plugin.py
- OpenAI Codex plugin JSON reference: https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/plugin-creator/references/plugin-json-spec.md

Verified implementation facts:

- A plugin manifest advertises MCP configuration through the `mcpServers` field when `.mcp.json` exists.
- Current OpenAI scaffold code creates `.mcp.json` using the wrapper `{ "mcpServers": {} }`.
- The plugin keeps `skills: "./skills/"` and adds `mcpServers: "./.mcp.json"`, making the plugin hybrid rather than replacing the skill.
- The deployed server key is `current_3d_engineering` rather than a hyphenated key. This avoids a current Codex tool-exposure edge case reported against hyphenated plugin MCP server keys while keeping the plugin's canonical name `current-3d-engineering` unchanged.
- `.mcp.json` contains only `type: "http"` and the HTTPS URL. No bearer-token environment variable, OAuth flow, custom authorization header, secret, or command-based local server is configured.

## Hosting and cost boundary

Hosting provider selected after Cloudflare was explicitly removed from the architecture: AppDeploy.

Current provider evidence checked before deployment:

- AppDeploy pricing and platform pages stated a Free tier at $0 with no credit card required and hosted HTTPS/backend capability under fair-use limits.
- No AppDeploy AI, database, storage, secrets, authentication, realtime, paid third-party API, custom domain, or other billable downstream dependency is used by this MCP.
- Hosting terms are provider-controlled and can change. The repository design therefore requires migration to another directly controllable $0 host rather than silently opting into a mandatory paid dependency if the current free-hosting constraint stops being true.
- AppDeploy's free-service terms grant the provider broad processing/license rights over content and deployment/QA data. This deployment contains already-public MIT-licensed repository guidance and no private project data, credentials, or user records. That provider tradeoff was disclosed before final wiring and should be re-reviewed if the hosted data scope changes.

## Deployment evidence

Initial AppDeploy deployment was blocked by TypeScript validation because the compact deployment copy of `backend/guidance.js` contained a serialization syntax error. No live-success claim was made from that attempt.

The guidance file was replaced with the canonical unminified source and the app redeployed. The first successful deployment passed all three user-visible E2E workflows but reported only 50% backend-route coverage because QA had not exercised `GET /api/mcp`.

The public self-check and QA contract were then strengthened so the primary workflow explicitly proves that GET is refused before anonymous POST initialization and tool discovery. AppDeploy's final same-app verification reported:

- deployment status: `ready`;
- E2E: 3 passed / 3 total;
- backend routes: 2 covered / 2 declared;
- endpoint coverage: 100%;
- unused endpoints: 0;
- frontend errors: 0;
- network errors: 0;
- backend errors: 0.

That same-app success was not treated as sufficient external MCP proof.

## Scope decision: bundled guidance

The approved design initially described runtime guidance as exact copies of the full repository Markdown files. During implementation, the hosted MCP instead received concise immutable guidance resources derived from the same governing rules. This is intentional:

- the remote endpoint does not fetch GitHub at runtime;
- responses remain bounded and deterministic;
- no external repository availability becomes a prerequisite for guidance access;
- the full local skill and reference Markdown remain authoritative for full project engineering behavior;
- the anonymous MCP is a smaller read-only companion rather than a second autonomous engineering agent.

The MCP tests and README describe this narrower contract explicitly. Future changes to hosted guidance must update the bundled resource source, tests, and deployment together.

## Local environment limitation

The conversation container could not resolve the AppDeploy hostname through DNS, so container-side `curl` was not accepted as deployment proof. External verification instead uses independent network paths:

1. AppDeploy's same-app E2E/endpoint-coverage evidence;
2. an independent Hatchable isolate issuing raw HTTPS requests to the public gateway; and
3. GitHub Actions live integration tests that read the canonical endpoint from `.mcp.json` and call the real HTTPS service.

Mocks are not substitutes for those external proofs.
